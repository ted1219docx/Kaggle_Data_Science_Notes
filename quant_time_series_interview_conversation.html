For your interview prep, treat a time-series project as the same broad workflow you already use for regression/classification, but with one extra principle running through the whole project:

time ordering must be respected everywhere.

Roadmap

1. Understand the structure of the data
- What does one row represent?
- One asset or many?
- What is the target?
- What is the sampling frequency?
- Are timestamps equally spaced?
- Are there duplicate timestamps or gaps?
- Could any variable only become known after the prediction time?

Typical checks:
df.shape
df.head()
df.info()
df.describe(include="all")
df["date"].min(), df["date"].max()

Then sort:
df = df.sort_values(["asset_id", "date"])

2. Perform data-quality checks
- missing values
- duplicates
- impossible values
- constant columns
- extreme values
- gaps in time

Example:
df["time_diff"] = df["date"].diff()
df["time_diff"].value_counts().head()

3. Plot the target through time
Look for:
- trends
- volatility clustering
- regime changes
- structural breaks
- non-stationarity
- unusual periods

Rolling summaries:
df["rolling_mean_20"] = df["target"].rolling(20).mean()
df["rolling_std_20"] = df["target"].rolling(20).std()

4. Understand the target distribution
Use describe() and histograms.
For returns, do not automatically delete extreme values because they may be real market events.

5. Investigate temporal dependence
Ask whether the past tells you anything about the future.

Lag correlation:
for lag in [1, 2, 5, 10, 20]:
    print(lag, df["target"].corr(df["target"].shift(lag)))

Also consider autocorrelation of absolute or squared returns because volatility can be persistent even when raw returns are not.

6. Split train and test chronologically
Avoid random train_test_split.

Example:
split_idx = int(len(df) * 0.8)
train = df.iloc[:split_idx]
test = df.iloc[split_idx:]

7. Create simple baselines
Start with zero/mean prediction, then linear regression.
Progression:
Naive baseline → Linear → Ridge/Lasso → Random Forest → Gradient Boosting

8. Engineer time-series features
Useful features:
- lagged values
- rolling mean
- rolling volatility
- momentum
- range features
- calendar features

For leakage safety:
past = df["target"].shift(1)
df["mean_20"] = past.rolling(20).mean()
df["vol_20"] = past.rolling(20).std()

9. Be extremely careful about leakage
Every feature should have a timestamp describing when it becomes observable.
At prediction time t, every feature must be known at or before t.

10. Use time-aware cross-validation

User
Every feature should have a timestamp describing when it becomes observable. -- how do I enforce it?
Assistant
You enforce it by making information availability time part of your feature-engineering logic, not necessarily by literally adding a timestamp column for every feature.

Suppose your target is y_t = r_{t+1}: predict the next-period return using information available up to time t.

Then every feature must satisfy:
feature information time <= t

Practical approach:
- Define the prediction timestamp explicitly.
- Build features only from rows available by that point.

Lagged returns:
df["ret_lag_1"] = df["return"].shift(1)
df["ret_lag_5"] = df["return"].shift(5)

Rolling features:
past = df["return"].shift(1)
df["rolling_mean_20"] = past.rolling(20).mean()
df["rolling_vol_20"] = past.rolling(20).std()

For multiple assets:
df = df.sort_values(["asset_id", "date"])
df["ret_lag_1"] = df.groupby("asset_id")["return"].shift(1)

Another leakage source is external features published with delay. Observation period and release time are different things. You should only use a feature once its release_time <= prediction_time.

For delayed data, pd.merge_asof is often useful:
pd.merge_asof(
    predictions.sort_values("prediction_time"),
    macro.sort_values("release_time"),
    left_on="prediction_time",
    right_on="release_time",
    direction="backward",
)

Preprocessing itself can leak information too. Fit scalers/imputers only on the training window, ideally inside a Pipeline.

A useful audit table is:
Feature | Source | Latest data used | Known at prediction time?

The subtle point is that current row does not automatically mean available. It depends on the exact prediction moment.

A good interview explanation:
“I first defined the prediction time and the information set available at that time. Lagged and rolling features were constructed only from observations available strictly before the prediction point, external variables were aligned by release time rather than observation period, and all preprocessing was fitted only on the training window.”

external features published with delay.

Could you explain in greater detail how we can handle this?
Assistant
This is one of the most important sources of subtle leakage in financial time-series work.

The core issue is that an external variable usually has at least two different dates:
1. The period the data describes
2. The time the data actually became known

Example:
economic_period | release_time | CPI
July            | 14 Aug 07:00 | 3.1
August          | 16 Sep 07:00 | 3.0

If you are predicting on 15 September, you cannot use August CPI just because it describes August. It had not yet been released.

The rule is:
release_time <= prediction_time

Why a normal merge is dangerous:
market.merge(macro, left_on="month", right_on="economic_period")
can leak future information.

Use merge_asof:
df = pd.merge_asof(
    market.sort_values("prediction_time"),
    macro.sort_values("release_time"),
    left_on="prediction_time",
    right_on="release_time",
    direction="backward"
)

This asks:
“For every prediction timestamp, what was the most recently released macro observation available?”

Three dates to think about:
- observation_period
- release_time
- prediction_time

Revisions are another subtle problem.
If GDP is first reported at 2.1% and later revised to 1.8%, a backtest for the earlier date should use 2.1%, not today's revised value.

That leads to point-in-time data:
“What value would I actually have seen if I had queried this dataset at time t?”

For company fundamentals:
quarter_end is not the same as announcement_time.
Use announcement_time to decide when a value becomes available.

For analyst estimates:
keep historical estimate snapshots, not only the final/latest value.

For credit ratings:
use effective_from / effective_to dates.

For weather and energy:
if predicting tomorrow's electricity demand today, use today's weather forecast for tomorrow, not tomorrow's actual temperature.

A useful data model:
external = DataFrame({
    "observation_period": ...,
    "available_from": ...,
    "value": ...
})

Then merge by prediction_time using merge_asof.

For multiple assets:
pd.merge_asof(
    market.sort_values(["ticker", "prediction_time"]),
    fundamentals.sort_values(["ticker", "release_time"]),
    left_on="prediction_time",
    right_on="release_time",
    by="ticker",
    direction="backward"
)

Audit it:
assert (
    df["release_time"].isna()
    | (df["release_time"] <= df["prediction_time"])
).all()

If you only know a fixed publication lag:
df["feature_available"] = df["feature"].shift(1)
or shift(2), etc., but explicit timestamps are safer.

If only daily dates are provided and exact release time is unknown, a conservative approach is to lag the feature until the next observation.

Missing external features can be structural temporal missingness: the new number may simply not have been published yet. Forward-filling can be valid after release-time alignment because you are carrying forward the latest known value.

Full workflow:
1. Identify what each observation refers to.
2. Find the publication/release timestamp.
3. Define exactly when predictions are made.
4. Align external data using release time.
5. Use latest value with release_time <= prediction_time.
6. Handle revisions using historical vintages if available.
7. Forward-fill only after correct alignment.
8. Assert that no release timestamp exceeds prediction time.

Concise interview explanation:
“Because the observation month and information-availability date are different, I align external data by release date rather than observation period. I use an as-of join to carry forward the latest value actually known at the prediction timestamp. If vintage data are available, I use the historical value known at the time rather than today's revised value.”
